# syncrona

## 1.2.0

### Minor Changes

- - New `bearer` auth method for a pre-issued OAuth access token, the counterpart of now-sdk's `SN_SDK_SESSION_BEARER_TOKEN`. Set `SN_BEARER_TOKEN` (optionally with `SN_AUTH_METHOD=bearer`, aliases `bearer-token` and `access-token`), and the CLI, the MCP server and the Fluent tier send `Authorization: Bearer <token>`. Like the SDK, a token in the environment is inferred ahead of every other method unless `SN_AUTH_METHOD` names a different one. The token is environment-only: `syncrona login` refuses `--auth-method bearer` and clears a stale `SN_BEARER_TOKEN` from `.env` on a re-login, and syncrona never refreshes the token. The per-profile `SN_BEARER_TOKEN_<PROFILE>` suffix works like every other auth variable.
- The `flow` table preset now also writes every custom Flow Designer action of the scope as a read-only, decoded `sys_hub_action_type_definition/<name>.action.json` document: the action, its inputs, outputs and output mappings, and its ordered steps with their added inputs and outputs, static input values and data-pill mappings. Secret-typed values are redacted, and `push` skips these documents with a warning.
- - Add a read-only Flow Designer reader in `packages/core/src/flow/`, the first step of native flow support. `readFlowDocument` reads one flow's `sys_hub_flow` row and every row that belongs to it (trigger, action, logic and subflow instances, inputs, outputs, variables and stages) through the Table API, decodes the base64 + gzip JSON payload columns (`values`, `trigger_inputs`, `subflow_inputs`, ...), and assembles the steps into a tree by `ui_id` / `parent_ui_id`, ordered by `order`. `serializeFlowDocument` writes the result as deterministic JSON (sorted keys, stable row order), so the same flow always produces the same bytes. Audit stamps are dropped; every other non-empty column is kept and each payload records its storage format, so it can be encoded back later. Steps with a missing parent, a repeated `ui_id` or a parent cycle stay in the document at the top level and are listed in `warnings`. No command uses it yet.
- Add the `flow` table preset: `refresh` and `download` write every Flow Designer flow and subflow of the scope as a read-only, decoded `sys_hub_flow/<name>.flow.json` document, with secret-typed values redacted. `push` skips these documents with a warning.
- Add the reverse of the flow decoder for the WP2 write path: `flowDocumentRecords` turns a `.flow.json` document back into the `sys_hub_*` rows it was assembled from (payloads re-encoded in their stored format, `flow` / `model` / `parent_ui_id` restored), and `flowDocumentChanges` returns only the rows an edit changes, inserts or deletes. Both return `record_update`-shaped records and refuse documents that would lose data on the way back (redacted secrets, re-parented steps, bad sys_ids). Nothing is written to an instance yet.
- Add `--engine sdk|native` to `syncrona fluent pack`, `install` and `status`. Without the flag those actions use `@servicenow/sdk` when it is installed and otherwise run on the native engine in `@syncrona/fluent`, so they no longer fail with the install hint when only the SDK is missing; `--dry-run` reports the fallback. `status` reports the engine it used (`engine` in `--json`). Any other action refuses `--engine`.
- - `syncrona fluent build` runs on syncrona's native engine, so build → pack → install works without `@servicenow/sdk`. Under the default `auto` engine the build falls back to native when the SDK is not installed, and `--engine native` forces it. The native build writes the compiler's records plus the `sys_app` scope record and the `package.json` and SBOM `sys_module` rows into the app output directory, byte for byte as SDK 4.13 writes them, with the SBOM naming syncrona as its tool. It honours `--frozen-keys` and `--skip-clean`. It refuses what it cannot build yet instead of building an incomplete app: server modules, client content, `metadata/` XML, runtime policies and a logo file. A build with errors writes nothing.
  - `@syncrona/fluent` exports `nativeBuild`, `moduleResolutionPath`, `sbomContent` and `FROZEN_KEYS_ERROR`.
- - The CLI no longer uses a scoped application's REST API on the instance. `init`, `refresh`, `download`, `push`, `status` and `doctor` talk to the Table API only: the manifest and the file contents are built from Table API reads, the session scope is read from the `apps.current_app` user preference (`sys_user_preference`), and an ATF step script is pushed by updating its `script` input in `sys_variable_value`. `SYNCRONA_SCOPED_API_PREFIXES` no longer affects the CLI, and `status` no longer reports a scoped-endpoint capability. Writing an ATF step script needs write access to `sys_variable_value`, which stock instance ACLs can refuse; a refused write fails that file with a 401/403 error instead of being retried.
- - Add a read-only Process Automation Designer playbook reader in `packages/core/src/flow/`, the playbook counterpart of the flow decoder. `readPlaybookDocument` reads one `sys_pd_process_definition` row and its lanes, activities, trigger instances, process inputs and outputs, variants and timer attributes through the Table API, plus the `sys_variable_value` rows that hold the `glide_var` columns (`launcher_inputs`, `start_rule_vars`, activity `inputs` / `outputs` / `type_vals`, `trigger_inputs`), which the Table API returns empty. `assemblePlaybookDocument` (schema `syncrona.playbook/1`) nests activities under their lanes ordered by `order`, attaches each row's variable values named by their dictionary element, decodes the JSON columns (`designer_state`, `permission`), drops audit stamps, and replaces secret-typed variable values and input defaults with `<redacted:type>`. Activities whose lane is not part of the playbook are kept under `unassigned` and listed in `warnings`. `serializePlaybookDocument` writes deterministic JSON. Runtime tables (contexts, executions, logs) are never read. No command uses it yet.
- - Add the playbook document writer in `packages/core/src/flow/`, the playbook counterpart of `flowFiles.ts`. `listScopePlaybooks` lists the `sys_pd_process_definition` rows of a scope, refusing a scope name that would add encoded-query conditions. `writePlaybookDocuments` / `syncPlaybookDocuments` write every playbook of a scope as `<source>/sys_pd_process_definition/<name>.playbook.json`, with the same file-naming rules as flow documents (unsafe characters become `_`, and names that collide case-insensitively get the sys_id appended). Files are written atomically and only when their bytes change; a playbook that cannot be read is reported without stopping the others, and documents left on disk that no listed playbook produced are reported as stale but kept. `isPlaybookDocumentPath` recognises the files. No command calls it yet; a `playbook` table preset will.
- Add the `playbook` table preset: `refresh` and `download` write every Process Automation Designer playbook of the scope as a read-only, decoded `sys_pd_process_definition/<name>.playbook.json` document, with secret-typed values redacted. `push` skips these documents with a warning.
- Inject a UI session into the Fluent tier, the counterpart of now-sdk's `SN_SDK_SESSION_TOKEN` / `SN_SDK_SESSION_COOKIE`. When `SN_SESSION_COOKIE` (with its `SN_SESSION_TOKEN` CSRF token) is set, the `fluent` actions hand that session to the SDK as is, ahead of the profile's method and without a login; a token without a cookie is refused. `FluentCredentialInput` gains a `session` kind, which `createFluentAuthResolver` returns unchanged. The variables are environment-only: `syncrona login` never stores them and clears stale ones from `.env`, and syncrona never renews the session. Other commands, and `fluent types --native`, keep using the profile.
- - Add a read-only decoder for legacy Workflows (`wf_workflow`) in `packages/core/src/flow/`, the Workflow counterpart of the flow and playbook documents. `readWorkflowRows` reads a workflow and its published version (the newest one when several are published, with the others named in `warnings`), the version's `wf_stage`, `wf_activity`, `wf_condition` and `wf_transition` rows, and the activities' `glide_var` values from `sys_variable_value`; runtime tables (`wf_context`, `wf_executing`, `wf_history`, logs) are never read. `assembleWorkflowDocument` builds one deterministic `syncrona.workflow/1` document: conditions nested under their activity, the `activity_stages` and `input` payloads decoded, audit columns dropped, secret-typed variable values and secret-typed values inside decoded payloads (gzip ones included) withheld as `<redacted:type>`, and dangling start activities, transition ends and conditions reported in `warnings`. `writeWorkflowDocuments` / `syncWorkflowDocuments` write every workflow of a scope as `<source>/wf_workflow/<name>.workflow.json` with the same file-naming (shared `documentFileNames`), atomic-write, per-document failure and stale-file rules as playbook documents, and `isWorkflowDocumentPath` recognises the files. The `workflow` table preset turns it on: `refresh` and `download` write the documents, and `push` skips them with a warning of their own.
- WP2 flow write path, offline part: `flowCompositeUpdate(doc, base?)` turns a flow document into the composite update the instance tracks a flow as (`sys_hub_flow_<sys_id>`: the flow followed by every row it owns, plus a `DELETE` for each row dropped from `base`), and `@syncrona/fluent` gains `serializeCompositeRecordUpdate(table, records)` to write it as one `record_update` document. Flow documents stay read-only in `push`; installing the result is not yet verified against a live instance.

### Patch Changes

- - `push` never sends `sys_id` or the audit stamps (`sys_created_by`, `sys_created_on`, `sys_updated_by`, `sys_updated_on`, `sys_mod_count`) from a `.meta.json` sidecar, even when an explicit `tableOptions.<table>.metaFields` lists them so they are pulled for reading; they are dropped and reported like read-only columns, so a hand-edited `sys_id` can no longer retarget the update and a stale audit stamp is no longer written back.
- - `push` of an ATF step's metadata alone (no `inputs.script` in the update) no longer calls the `pushATFfile` route with no script: it failed the metadata push on an instance without the route, and on one with it asked the server app to blank the step script.
  - A missing `pushATFfile` route is no longer retried: the wrapped error dropped the 4xx status, so `push` retried it and `dev` requeued it as a transient failure.
  - An editor backup (`script.js~`, `script.bak`, `script.tmp`) no longer counts as a field's local file on the download side: `refresh` and `repair` reported a deleted `script.js` as present, and `download` kept the backup instead of restoring it, while `push` ignored the backup — so the field could be neither pulled nor pushed.
  - `mirror sync` / `mirror status` now apply the CLI's TLS settings (`SYNCRONA_CA_BUNDLE`, `SYNCRONA_TLS_REJECT_UNAUTHORIZED`, the mTLS client certificate) to the OAuth token request and to every sweep request; they used the platform defaults, so an instance behind a private CA or requiring a client certificate failed where every other command worked.
  - `mirror sync --full` prints the finished sweep's commit message (and its `--json` document) before the post-sweep `git repack`, so a failed repack still exits 1 but no longer swallows a result `mirror report` cannot regenerate.
- - A JSON field file that is not valid JSON is refused with Node's parse message alone; the line and column it already names are no longer appended a second time.
  - A JSON field file is also withheld on download when an `Authorization` header holds a value, or when a credential-named key sits inside a JSON document stored as a string (a component's `props`, a tool's `inputs`); before, both reached the working tree.
  - The metadata sidecar no longer carries a JSON column that holds a credential (an AI tool's `tool_attributes` without the `ai` preset, for example): the column is left out with a warning, as the `.json` field file already was, and push leaves the instance's value alone.
- - An instance profile that names its own instance (`SN_INSTANCE_<P>`) no longer borrows the unprofiled `SN_BEARER_TOKEN`: the token belongs to `SN_INSTANCE`, and inferring bearer auth from it sent it to the profile's instance instead of the profile's own credentials.
  - `syncrona login --auth-method bearer-token` (or `access-token`, any spelling `SN_AUTH_METHOD` accepts for bearer) now explains that a bearer token is environment-only, instead of rejecting it as an unknown method.
- - A playbook document withholds secret-typed values inside its decoded payloads (`designer_state`, gzip-encoded columns), as a flow document already did; before, only variable values and input defaults were redacted.
  - A secret-typed input default or static value whose text was gzip-encoded JSON is withheld in flow, action and playbook documents; the assembler had decoded it into `payloads`, where the redaction never looked.
  - Reading an action with many steps sends its step ids in batches of 100, as the flow reader already did; one `IN` list of every step id could exceed the URL length the instance accepts.
  - A document folder that cannot be created (a file in its place, no permission) fails the flow or playbook documents it would hold instead of aborting the run; the custom-action documents are still written after a flow folder failure.
  - Flow, action and playbook document file names are compared the way the file system compares them (Unicode normalization as well as case), and a generated `<name>_<sys_id>` that another record's real name spells falls back to the bare sys_id, so two records never write the same file.
- - Flow documents now hold the steps of flows built on the older step model. Such flows (many shipped ones among them) have no rows in the `*_instance_v2` tables, so their documents used to have empty step lists. The reader now falls back to `sys_hub_trigger_instance`, `sys_hub_action_instance`, `sys_hub_flow_logic` and `sys_hub_sub_flow_instance` where the v2 tables are empty (the trigger is decided on its own; the steps are decided as a group). It attaches each step's inputs from `sys_variable_value` as `variableValues`, and inputs of a secret type are redacted like the v2 ones. A migrated flow's stale pre-migration copies are left out, so they no longer show up as `repeats ui_id` warnings.
  - `outputs_assigned` and `flow_variables_assigned` are kept as plain fields (they are comma-separated name lists), so they no longer raise false "could not be decoded" warnings. A gzip `values` payload with leading whitespace now decodes.
  - Writing a flow document back (`flowDocumentRecords` / `flowDocumentChanges`) sends older-model triggers and steps to their own tables and their inputs to `sys_variable_value`.
- - Re-author the ServiceNow REST client (`snClient`) without upstream-derived code: the retry loop, OAuth token wiring, Table API and user-preference calls, client cache and response unwrap helpers have their own structure, with identical requests, retries and error mapping (IND-7, slice 7a).
- - Internal: `FileUtils` and the download pipeline are re-authored in this project's own code (IND-7b). Behaviour, the on-disk layout, manifest handling and the exported API are unchanged; the missing-file scan now collects into one ledger, and new tests pin its answer shape.
- Internal: the push pipeline and the `push` command are re-authored from scratch (IND-7, slice 7c). Push behaviour, prompts, guards and exit codes are unchanged.
- Core internals re-authored as the project's own code (IND-7, slice 7d): the logger, push/build result reporting, scope and update-set switching, the built-in table defaults, the build plugin manager, the command handlers, the setup wizard and the CLI option table. Behaviour is unchanged apart from wording: the scope-mismatch, dev-mode, setup-complete and missing-config messages and the `push --scope-swap` / `--update-set` and `download` help texts are reworded, the watch-mode push summary no longer prints emojis, and a generated `sync.config.js` spaces its empty `excludes` / `includes` / `tableOptions` and `refreshInterval` entries like the other keys.
- - New opt-in `tablePresets` config (`"uib"`, `"workspace"`, `"ai"`): the JSON columns of UI Builder, workspace and AI Agent configuration tables are synced as `.json` field files instead of strings in the `.meta.json` sidecar — every `json` / `json_translations` column plus the string columns the preset names (for example `sys_ux_macroponent.composition`), on both the Table API build and the scoped-endpoint manifest. Unknown preset names fail config validation; tables switched off in `includes`/`excludes` stay off.
  - Download pretty-prints a JSON field file only when the stored value is canonical minified JSON, and writes every other value byte for byte. Push refuses a `.json` field file that is not valid JSON and minifies a file that is exactly the 2-space form of its value, so a round trip leaves the instance unchanged. This applies to every `json`-typed field file, not only preset tables: an existing minified `.json` field file is rewritten pretty-printed by the next download.
  - A JSON field whose value holds a non-empty string under a credential-named key (`password`, `api_key`, `client_secret`, `access_token`, …) is withheld on download with a warning naming the key path.
  - `push` refuses `sys_uxf_snapshot` records, which UI Builder generates on publish.
- `tablePresets`: the preset table lists were checked against a live instance's dictionary. `uib` adds `sys_ux_atf_action`, `workspace` adds `sys_ux_keyboard_shortcut_deny_list` and `par_component`, and `ai` adds the Generative AI feature mappings and the OneExtend (Now Assist skill) capability, definition, attribute and resource-mapping tables. Per-user and analytics tables stay out.

## 1.1.0

### Minor Changes

- fb75e72: `syncrona fluent` accepts a mutual-TLS client certificate (`SN_CLIENT_CERT` / `SN_CLIENT_KEY`) with a Basic or OAuth profile instead of refusing it. Core hands the TLS settings to the Fluent engine as `tls`, the OAuth token request presents the certificate, and the engine installs a TLS-configured fetch dispatcher for the duration of each instance-side action, restoring the previous one afterwards. `SYNCRONA_CA_BUNDLE` and `SYNCRONA_TLS_REJECT_UNAUTHORIZED` now apply to the Fluent tier as well. API-key profiles are still refused.
- 24156cf: now-sdk parity: SyncroNow AI covers the everyday ServiceNow SDK (`now-sdk`) workflow without giving up the file-based tier.

  - `query <table>` reads records with the `now-sdk query` flags (all but `-s/--select` and `-a/--auth`) and JSON envelope; the table name must be letters, digits and underscores, and `--timeout` at least 1.
  - `cicd <action>` drives `api/sn_cicd`: `run-suite`, `run-test`, `install`, `publish` and `rollback`, with exit codes 0 (pass), 1 (could not finish) and 2 (failures). `--progress-id` resumes waiting on a run that outlived `--timeout` without dispatching it again; `--json` prints a failure document (with the `progressId` to resume) when the run could not finish, and `--poll-ms` is kept between 250 and 60000.
  - `fluent <action>` drives Fluent projects through the new optional `@syncrona/fluent` package (`@servicenow/sdk` is an optional peer, `~4.13`), reusing the syncrona credential store for Basic and OAuth profiles. `fluent init` writes a default project version (`0.0.1`) and the loaded SDK version into `package.json`, the CLI warns once when the SDK is outside `~4.13`, and `fluent install` refuses to prompt without a terminal or with `--json` (pass `--ci`).
  - `push --create` / `--no-create` creates or adopts records for unmapped local files (also `createRecords` in `sync.config.js`). On a table outside the `sys_metadata` hierarchy, which has no `sys_scope` column, the idempotency lookup and the POST body leave the scope out, and `sys_choice` is matched on its natural key (`name`, `element`, `value`, `language`, `dependent_value`). `push --prune` deletes in-scope records whose tracked files git shows deleted. Prune refuses while a download is unfinished, when `sourceDirectory` is blank, missing or empty, and above 25 deletions or 20% of the manifest without `--allow-mass-delete`; under `--ci` it needs `--diff`, a path or that flag. A record the instance no longer has (404) is reported as unverified and keeps its manifest entry, and a table that is both pruned and created gets a rename warning. `push --create` refuses to adopt an instance record the manifest already tracks under another name, or one another candidate of the same run adopted, and `push --prune` holds the DELETE of a record whose sys_id the same run's creation plan matched (a rename, not a deletion) — in the dry run and the real run alike; a record renamed on the instance is picked up with `syncrona refresh`. Idempotency lookups read back the key columns and fail closed when one is missing or its value differs (including a case-only difference), the `sys_choice` natural key includes `dependent_value` (empty and missing match alike), a key value containing `^` cannot be created or adopted because encoded queries cannot escape it, and a flat-layout prune target such as `Foo~Bar~script.js` matches only the record `Foo~Bar`. A record created from a `.meta.json` sidecar on a table the manifest does not describe yet, such as any table of a new scope that owns no records, reads the sidecar columns from the dictionary first, on any table rather than only on data-model tables. New data-model records are created table first, then columns, then choices, under the per-record layout too, so a new table and its column can be created in one push. `push --create --dry-run` builds each create's body as the real run does, sidecar discovery included, so a create the real run would refuse is previewed as an error.
  - While `cicd` or `sync_cicd_run` waits on a run, a poll that fails transiently (a network failure, 408, 425, 429 or a 5xx, including an OAuth token endpoint 5xx) is retried up to 3 times in a row, one `pollMs` apart and one request per poll on both sides, before the run is reported as could-not-finish (`incomplete`); any other poll error still ends the run at once. A network failure is judged by its code, its own or its cause's (a socket reset, a refused connection, an undici socket error or a timeout), so a client-side bug, a malformed HTTP answer or a rejected OAuth token is no longer retried as if the instance had not answered.
  - With OAuth, a token endpoint that rejects the first token request costs one token request in the core CLI, as in `sync_cicd_run`; it used to force a second grant, and the request was never sent either way.
  - `cicd` reports a progress poll answered with a client error (400, 401, 403, 404, ...) at once, naming the status and the `GET api/sn_cicd/progress/<id>` request, instead of the bare transport message; three transient failures in a row name the request too. A run that reaches `--timeout` while polls are still failing now ends with the timeout error (last status and last poll error) rather than the transport error, and every timeout says where to check the tracker on the instance and how to resume it with `--progress-id` (exit 1).
  - `cicd` retries a progress poll answered with 408 (request timeout) like 429 and 5xx, and reports a 3xx answer (a 304, or a redirect the client did not follow, naming its `Location` when it has one) to a progress poll, the dispatch or the ATF result read as an unexpected 3xx answer, usually a proxy or an SSO/login gateway in front of the instance, with the text `sync_cicd_run` uses, instead of a client error or a bare "Request failed with status code 304"; it is not retried. An HTML page answered in place of JSON (a body starting with `<`; a JSON body is read as JSON whatever its content type says, as `sync_cicd_run` reads it) and a redirect loop end the run at once as a session/authentication redirect, instead of a missing `result` or a no-response poll that is retried. Its sn_cicd requests follow at most 20 redirects, the limit `sync_cicd_run`'s fetch has, so a redirect loop costs the same 21 requests on both sides.
  - `cicd` and `sync_cicd_run` decide an ATF verdict from an allow-list: a suite passes only with status `success` or `success_with_warnings` and zero rolled-up failures and errors, and an unknown status or count is reported as could-not-finish (exit 1) rather than a pass. Resuming an ATF tracker with `--progress-id` as `install`, `publish` or `rollback` is refused.
  - `sync_cicd_run` (and `cicd`, which shares the verdict) no longer reports a suite that executed zero tests as passed: a passing suite status with a stated success count of 0 (an empty suite, or every test skipped) is `failed` / exit 2 with "the suite ran no tests", and one whose success count is missing or unreadable is `incomplete` / exit 1. Resuming a successful tracker that links no ATF result as `run-suite` or `run-test` is refused as `incomplete` rather than read as a pass, and a failed or cancelled one is reported as ending before any test result rather than as failing tests.
  - `cicd --progress-id` (and a `sync_cicd_run` resume) over an ATF tracker that ended in error or was cancelled before it linked a result now exits 2 / `failed` like the dispatched run, saying no test results were reported (and that an app-repo tracker would be resumed with its own action), instead of exit 1 with a resume-as-install hint.
  - `cicd --progress-id` (and a `sync_cicd_run` resume) over a finished ATF tracker whose result answers 404 now says the progress id may belong to the other ATF kind (a suite run resumed as `run-test`, or the reverse) and names the action to resume it with, instead of an endless "re-run with --progress-id" hint.
  - `cicd --json` documents carry a `verdict` (`passed`, `failed`, `no_tests`, `incomplete` when the run could not be followed to its end, `unknown` when the tracker finished but its ATF result was unreadable or unclear) and a `reason`, success and failure documents alike; the failure document keeps its `error` field.
  - `sync_cicd_run` polls again on 408 and 425 like core, sends each sn_cicd request once (its poll loop owns the retries, so a persistent failure costs the same 3 requests as in core), and reports a 3xx answer as an unexpected 3xx answer (usually a proxy or an SSO/login gateway) instead of a failed request; it is not retried. An HTML page in place of JSON (a body starting with `<`) and a redirect loop are reported like core, as a session/authentication redirect that is not retried.
  - `sync_cicd_run` ends every timeout like `cicd`: the message gives the budget in seconds, the last status (and the last poll error when polls were failing at the deadline, which now ends with the timeout rather than the transport error), where to check the tracker (its link, the dispatch answer's link, or `GET api/sn_cicd/progress/<id>`) and how to resume waiting with `progressId` and a larger `timeoutMs`.
  - `sync_cicd_run` responses carry an additive `verdict` with the values `cicd --json` reports (`passed`, `failed`, `no_tests`, `incomplete`, `unknown`), so an `incomplete` outcome tells a run that could not be followed apart from a finished tracker whose ATF result was unreadable or unclear, and an additive `reason` with the values `cicd --json` reports, set in the same cases, in full and possibly over several lines; both are documented in the tool description, which also states that a rejected call (an unknown action, an invalid argument or a missing `confirmDestructive`) returns only an error text, with neither field.
  - `run_workspace_command` now asks for confirmation before `cicd`, `dev`, `refresh`, `init --new`, `repair --apply` and every `fluent` action except `status`, `explain` and `types` (without `--out`).
  - New MCP tool `sync_cicd_run` exposes the same `api/sn_cicd` actions to AI clients, gated by `confirmDestructive` with `dryRun` support and audit logging; it reports `succeeded` / `failed` / `incomplete` with the CLI exit code. An optional `progressId` resumes polling an `incomplete` run's tracker instead of dispatching new work.
  - New MCP tool `sync_fluent_build` runs `fluent build` for a Fluent project inside the workspace through the optional `@syncrona/fluent` package, with the CLI's `frozenKeys` / `errorOnConflict` / `skipClean` flags, `dryRun` support and audit logging; it returns errors, warnings and output paths with the CLI exit code, and a structured error with the install hint when the package or `@servicenow/sdk` is missing (63 MCP tools). Errors and warnings are capped at 200 each (with counts and truncation flags), output listing does not follow symlinks, and a missing optional package is detected by the exact module name.
  - `SN_MAX_RPS` lowers the 20 requests/second cap for the CLI and the MCP server (a whole number from 1 to 20; an invalid value is an error, never a silent full rate).
  - `init --new --name` creates a new scoped application and binds the directory to it, writing an empty manifest with the new `scopeId` when the app owns no records yet (a later `refresh` keeps that `scopeId`); the existing-app check queries `sys_scope`, so a store app of the same scope is found too. `download` of an existing scope that owns no records still refuses instead of writing an empty manifest. A `refresh` of that empty manifest keeps it, reports at info level that the scope owns no records yet, and exits 0, so `dev` no longer logs an error on every interval; a manifest without a `scopeId` still refuses an empty discovery.
  - `download <scope> --ci` for a scope that owns no records yet still refuses without prompting and exits 1, and the refusal now says so: a new scope has nothing to download until it owns a record, and `init --new` is the way to bind a scope that is still empty.
  - Opt-in `dataModelTables` tracks data-model records (tables, columns, choices) as editable local files.

## 0.9.4

### Patch Changes

- Record metadata now works on every instance, not just the ones without the
  companion scoped app. `0.9.3` announced the `.meta.json` sidecar, but the scoped
  manifest the companion app returns carries no metadata layer, so a `refresh` or
  `download` against an instance that has the app installed produced scripts and no
  sidecars at all. The scoped manifest is enriched before it is used, and the
  sidecar half of a fetch goes over the Table API while the scoped endpoint keeps
  serving the file half.

  Three further corrections to the same layer:

  - Every tracked column is captured. Discovery excluded anything named `sys_*`,
    which dropped `sys_scope`, `sys_class_name`, `sys_policy` and their siblings;
    the exclusion is now six named audit stamps (`sys_id`, `sys_created_by/on`,
    `sys_updated_by/on`, `sys_mod_count`). On a five-table scope the tracked
    columns per table went 29→40, 14→25, 9→17, 34→45 and 8→18.
  - A column that is empty on the instance is written as `""` instead of being
    omitted, so the sidecar answers "what can I set on this record?" rather than
    only "what is set right now". A column the instance did not return at all — a
    read ACL hides it — is still left out rather than claimed as empty.
  - A sidecar whose manifest carries no metadata layer is no longer dropped in
    silence: `push` resolves it from the record it sits under, an unreadable
    dictionary is reported per table with its cause and both escape hatches, and a
    metadata push against a degraded manifest names `syncrona refresh` instead of
    reporting every key of a correct file as an unknown column.

  Enrichment also stopped re-reading a scope's shared ancestor table once per
  table: 15 requests down to 11 on the same scope.
